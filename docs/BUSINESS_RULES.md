# Money Context Business Rules

이 문서는 Money Context의 재정 의미와 계산 규칙을 고정한다. UI, DB, 통계, Export는 모두 이 규칙을 동일하게 사용해야 한다.

# 1. 재정 데이터의 네 축

## 1.1 소비(Consumption)

무엇을 언제 얼마에 구매/사용했는지 나타낸다.

예: 8월 20일 노트북 900,000원 3개월 할부 구매 → 8월 소비 900,000원.

## 1.2 현금흐름(Cash Flow)

실제 현금성 자산이 언제 들어오고 나가는지 나타낸다.

같은 900,000원 3개월 할부라면 카드 결제계좌 현금흐름은 결제 스케줄에 따라 300,000원씩 발생할 수 있다.

## 1.3 재정 상태(Financial Position)

특정 시점의 자산, 일반 부채, 카드 미결제를 반영한 상태다.

```text
순자산 = 자산 - 일반 부채 - 카드 미결제액
```

## 1.4 미래 계획(Forecast)

예정 거래, 반복 거래, 카드 결제, 저축 계획을 반영한 미래 현금흐름이다.

# 2. 거래 유형

## INCOME

- 자산 증가
- 수입 통계 포함
- 현금흐름 포함
- 소비 통계 제외

## EXPENSE

- 소비 통계 포함
- 예산 사용량 포함
- 현금/은행/체크 결제라면 연결 자산 감소
- 신용카드 결제라면 카드 미결제 증가

## TRANSFER

- 한 자산/계정에서 다른 자산/계정으로 이동
- 수입 통계 제외
- 소비 통계 제외
- 예산 제외
- 총자산은 원칙적으로 변하지 않음

카드대금 납부도 TRANSFER의 특수한 형태로 본다.

## ADJUSTMENT

실제 잔액과 시스템 계산 잔액을 맞추는 특수 거래다.

- 계좌 잔액에는 반영
- 순자산에는 반영
- 수입/소비 통계 제외
- 예산 제외

# 3. 계좌 유형

## BANK / CASH

독립적인 유동자산이다.

## DEBIT

체크카드/직불 결제수단이다. 자체 자산을 갖지 않고 `linked_account_id`의 BANK 자산을 사용한다.

DEBIT와 BANK를 동시에 자산 합계에 넣지 않는다.

## CREDIT_CARD

자산이 아니다. 신용카드 소비와 미결제 부채, 향후 결제 스케줄을 나타낸다.

## LIABILITY

대출, 빌린 돈 등 일반 부채다.

# 4. 잔액 계산

BANK/CASH의 계산 잔액:

```text
initial_balance
+ confirmed income
- confirmed expense paid directly by this asset
+ incoming transfers
- outgoing transfers
+ adjustments
```

PENDING/CANCELLED 거래는 실제 잔액 계산에서 제외한다.

DEBIT 지출은 연결된 BANK 계좌 지출로 반영한다.

# 5. 신용카드

## 5.1 카드 구매

신용카드로 100,000원을 지출하면 구매일에 소비 100,000원이 발생하고 카드 미결제가 100,000원 증가한다.

연결 은행계좌 잔액은 구매일에 감소하지 않는다.

## 5.2 카드대금 납부

결제일에 BANK → CREDIT_CARD 이체를 기록한다.

- 은행 잔액 감소
- 카드 미결제 감소
- 새로운 소비 0원
- 예산 사용량 추가 0원

## 5.3 카드 한도

```text
남은 한도 = credit_limit - 현재 카드 미결제 원금 성격 금액
```

수수료를 한도에 포함할지는 카드사의 실제 처리와 다를 수 있으므로 시스템 표시에서는 미결제 총액과 한도 사용액을 구분할 수 있게 설계한다.

# 6. 할부

900,000원 3개월 무이자 구매 예시:

```text
구매일 소비: 900,000
카드 미결제: +900,000
1회차 결제 현금흐름: 300,000
2회차 결제 현금흐름: 300,000
3회차 결제 현금흐름: 300,000
```

회차 납부가 발생할 때 새로운 EXPENSE를 만들지 않는다.

유이자 할부인 경우:

- 구매 원금 소비는 구매일에 인식
- 할부 수수료는 실제 발생하는 별도 비용으로 인식 가능
- 수수료는 `fee_amount`로 회차별 관리

# 7. 예정 거래

PLANNED 상태:

- 실제 수입/지출 통계 제외
- 실제 예산 사용률 제외
- 미래 현금흐름 포함
- 예정 포함 예산 전망에는 포함

CONFIRMED로 전환될 때 실제 transaction과 연결한다.

# 8. 반복 거래

`AUTO_CONFIRM`은 실행일에 CONFIRMED transaction을 생성한다.

`REQUIRE_CONFIRMATION`은 실행일에 PENDING transaction을 생성한다.

반복 규칙을 변경해도 이미 생성된 과거 transaction은 변경하지 않는다.

# 9. 예산

## 9.1 실제 사용률

CONFIRMED EXPENSE만 포함한다.

다음은 제외한다.

- TRANSFER
- ADJUSTMENT
- 카드대금 납부
- CANCELLED
- PENDING
- PLANNED 예정 거래

## 9.2 예정 포함 예상 사용률

```text
확정 지출 + 분석 기간 내 planned expense
```

을 사용한다.

## 9.3 이월

이월이 활성화된 카테고리:

```text
이번 달 사용 가능 예산 = 기본 예산 + 전월 rollover
이번 달 rollover = 이번 달 사용 가능 예산 - 이번 달 실제 사용액
```

양수/음수 모두 다음 달에 전달한다.

# 10. 급여 사이클

급여일이 10일이면 예시 사이클은:

```text
2026-08-10 00:00:00 Asia/Seoul
~
2026-09-09 23:59:59 Asia/Seoul
```

월별 통계는 항상 달력 월과 분리한다.

# 11. 자유 사용 가능 금액

개념식:

```text
현재 유동자산
- 아직 반영되지 않은 카드 미결제 중 보호할 금액
- 다음 급여일까지 예정된 필수 지출
- 다음 급여일까지 발생할 반복 고정비
- 다음 급여일까지 예정된 저축 적립
- 보호금액
= 자유 사용 가능 금액
```

같은 금액을 두 번 차감하지 않아야 한다.

예를 들어 카드 미결제액을 전액 차감했다면 해당 카드 결제 예정 거래를 다시 차감하지 않는다. 계산 엔진은 항목별 provenance를 유지하거나 중복 방지 규칙을 명확하게 가져야 한다.

# 12. 하루 사용 가능 금액

```text
max(0, 자유 사용 가능 금액) / 남은 일수
```

남은 일수에는 현재 날짜를 포함할지 여부를 제품 전체에서 동일하게 정의한다. Money Context에서는 **오늘을 포함한 남은 캘린더 일수**를 사용한다.

# 13. 저축 목표

```text
현재 적립액 = savings_contributions 합계
남은 필요 금액 = max(0, target_amount - 현재 적립액)
```

목표일까지 남은 월 적립 횟수는 `Asia/Seoul`의 목표일과 현재일을 기준으로 계산한다.

목표일이 지났고 목표액 미달이면 `OVERDUE` 상태로 표현한다.

# 14. 외화

거래 입력 시:

- `amount`: 원통화 금액
- `currency`: 원통화 코드
- `base_amount`: 입력 시점 KRW 환산 금액
- `exchange_rate`: 사용한 환율

과거 통계/Export에서는 `base_amount`를 사용한다.

# 16. 카테고리와 태그의 역할

## 16.1 Category — 무엇에 사용했는가

소비 대상을 나타낸다. 예: 식비, 교통, 운동, 취미, 쇼핑.

## 16.2 Tag — 왜/어떤 맥락에서 사용했는가

소비 맥락을 나타낸다. 예: 운동식단, 데이트, 회사, 여행, 친구모임, 홋카이도.

## 16.3 예시

```text
통밀식빵 + 땅콩버터
Category: 식비
Tag: 운동식단
```

```text
프로틴
Category: 운동
Tag: 보충제
```

Category는 "무엇"을, Tag는 "왜/어떤 상황"을 답한다. 새 카테고리/태그를 만들 때도 이 기준을 유지한다. 기존 거래의 카테고리/태그를 이 기준에 맞춰 임의로 재분류하지 않는다.

# 17. 기간 잉여금과 저축 목표 적립액

## 17.1 기간 잉여금(Period Surplus)

```text
period_surplus = income - expense
```

수입에서 지출을 뺀 값은 **저축이 아니라 기간 내 잉여금**이다. 저축 목표에 실제로 적립되지 않았다면 그 돈은 남아있을 뿐 저축된 것이 아니다.

## 17.2 저축 목표 적립액(Savings Goal Contributions)

```text
savings_goal_contributions = 분석 기간 내 savings_contributions.amount 합계
```

`savings_contributions.contribution_date`가 분석 기간에 속하는 적립 기록만 합산한다. **Money Context 저축 목표에 연결된 적립 기록만** 이 값에 포함되며, 목표에 연결되지 않은 별도 저축(예: 목표를 지정하지 않고 적금 계좌로 이체한 돈)은 포함하지 않는다. 따라서 "사용자의 모든 실제 저축 행위"를 의미하지 않으며, 기간 잉여금과도 동일하게 계산하지 않는다.

## 17.3 비율

```text
surplus_rate = period_surplus / income
savings_goal_contribution_rate = savings_goal_contributions / income
```

수입이 0이면 두 비율 모두 계산 불가로 표시한다(0으로 나누지 않는다).

# 18. 외부 자금 이동과 결제수단 통계

## 18.1 내부 이체

`from_account_id`와 `to_account_id`가 모두 존재하는 TRANSFER는 사용자 소유 계좌 간 이동이다. 수입/지출/결제수단별 소비 통계에서 모두 제외한다.

## 18.2 외부 송금 / 외부 수입

한쪽 계좌 정보만 있는 TRANSFER(한 사이드만 존재)는 외부로 나가거나 외부에서 들어온 자금이다.

- 외부 송금(`from_account_id`만 존재): 지출 통계에 포함한다. 결제수단별 소비에서는 실제 출금 계좌 이름이 있으면 그 계좌로 집계하고, 계좌 이름을 확인할 수 없는 경우에만 "외부 자금 이동"으로 별도 집계한다. "미지정"으로 집계하지 않는다.
- 외부 수입(`to_account_id`만 존재): 수입 통계에 포함하되 결제수단별 소비 통계에는 포함하지 않는다.

## 18.3 "미지정" vs "외부 자금 이동"

"미지정"은 EXPENSE 거래인데 결제 계좌 정보 자체가 누락된, 진짜 데이터 누락 사례에만 사용한다. "외부 자금 이동"은 거래의 성격이 외부 자금 이동이기 때문에 결제수단이 없는 경우에 사용한다. 두 값을 같은 의미로 취급하지 않는다.

## 18.4 외부 자금 이동은 수입/지출과 별도로 더하는 금액이 아니다

Export의 "외부 자금 이동" 섹션(외부 송금/외부 수입 합계)은 이미 위 기간 수입/지출 합계 안에 포함된 **부분집합**이다. 외부 AI가 이 값을 기간 지출·수입에 추가로 더해 이중 계산하지 않도록, Markdown 섹션 제목과 해석 주의사항에 "이미 포함됨"을 명시하고 JSON에서는 `external_flows.included_in_period_totals: true`로 표시한다.

# 19. 거래의 반복/일회성 성격(Expense Nature)

GPT Export가 소비 추세를 단순 연장(extrapolation)하지 않도록, 지출 거래를 다음 세 가지로 분류한다.

```text
RECURRING
ONE_TIME
UNKNOWN
```

- `recurring_rule_id`가 있는 거래(반복 거래 규칙이 생성한 거래)는 RECURRING이다.
- `planned_transaction_id`가 있는 거래(사용자가 등록한 예정 거래가 확정되어 생성된 거래)는 ONE_TIME이다.
- 그 외 모든 거래는 UNKNOWN이다. 근거 없이 ONE_TIME으로 추정하지 않는다. 기존 데이터를 이 기준으로 소급 재분류하지 않는다.

`예정 거래(planned transaction)`와 `반복 거래(recurring transaction)`는 서로 다른 개념이다. 예정 거래는 반복 규칙 없이 등록된 미래의 단일 이벤트(예: "다음 주 차량 수리 300,000원")일 수 있으므로, **예정 거래에서 확정되었다는 사실만으로 RECURRING으로 판정하지 않는다.** `planned_transaction_id`가 있는 거래는 위 기준대로 항상 ONE_TIME이다.

# 20. 삭제/수정 규칙

- 과거 거래 수정 시 관련 통계는 재계산한다.
- 카드 거래 수정 시 카드 미결제/결제 예정도 재계산한다.
- 할부 원본 거래를 삭제하려면 연결된 installment plan 처리 방식을 명시적으로 선택하도록 한다.
- 이미 거래에 사용된 계좌/카테고리는 기본적으로 hard delete 대신 inactive 처리한다.
