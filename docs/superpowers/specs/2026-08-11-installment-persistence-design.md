# Installment Persistence Design

## Goal

Persist a confirmed KRW credit-card purchase, its installment plan, and every scheduled payment atomically. Allow a later card-settlement transfer to be linked to exactly one scheduled payment without creating another expense.

## Scope

- Reuse the existing `installment_plans` and `installment_payments` tables.
- Extend the installment domain module with deterministic payment-schedule construction.
- Add a server-only installment repository and service. The transaction service remains responsible for ordinary transactions.
- Add two authenticated PostgreSQL RPCs: one creates the purchase, plan, and payments; the other links a payment to a settlement transfer and marks it `PAID`.
- Test database atomicity, ownership/RLS, schedule persistence, and settlement linkage.

Out of scope: UI entry, automatic settlement matching, non-KRW installments, installment cancellation/editing, and separately materializing fee expenses. Fees are persisted on payment rows for later reporting.

## Data Flow

`createInstallmentPurchase` validates integer KRW amounts, an active owned `CREDIT_CARD` account, a positive installment count greater than one, and a valid Seoul purchase timestamp. It invokes `create_installment_purchase` once. The RPC inserts a confirmed `EXPENSE`, inserts its one-to-one `installment_plans` row, then inserts schedule rows generated by the service. A failure in any insert rolls back all inserts.

The schedule allocates principal using the existing deterministic remainder rule. It uses the supplied first payment date and advances by calendar months, clamping the day to the last day of each target month. Each payment stores its principal, fee, `SCHEDULED` status, and no settlement link.

`linkInstallmentSettlement` invokes `link_installment_settlement`. The RPC requires that the payment, plan, source BANK/CASH account, target plan credit-card account, and transfer all belong to `auth.uid()`. It inserts one confirmed `TRANSFER` from the payment account to the plan card, writes that transfer ID to the payment, and sets it to `PAID`. A payment already linked or paid is rejected. The transfer remains a transfer, so it cannot become a new expense or budget item.

## Boundaries

- `src/domain/cards/installments.ts`: pure schedule and fee validation; no database calls.
- `src/server/installments/service.ts`: input validation, account checks, and repository orchestration.
- `src/server/installments/repository.ts`: Supabase RPC calls and user-scoped reads needed by validation.
- Migration: transactional database mutations and defense-in-depth ownership checks. Existing generic RLS and ownership triggers remain in effect.

## Error Handling

Reject malformed integer amounts, non-KRW input, inactive/non-card purchase accounts, invalid dates, invalid fee arrays, non-owned accounts, a duplicate settlement link, and a settlement whose target is not the installment card. Do not partially persist any resource when creation or linkage fails.

## Testing

- Unit tests cover month-end schedule clamping, deterministic principal allocation, and fee preservation.
- Service tests cover card/account validation and repository calls.
- Supabase integration tests prove one purchase yields one expense, one plan, and N schedule rows; failed creation leaves no purchase; users cannot read or link another user's payment; and a linked settlement is one transfer with no EXPENSE transaction.

## Security and Financial Invariants

- All data access is constrained to the authenticated user; RPCs derive the caller from `auth.uid()`.
- RPCs use `security definer`, a fixed `public` search path, revoked public privileges, and authenticated-only execute grants.
- Amounts are integer KRW values in application code and `numeric` in PostgreSQL.
- The original card purchase is the only expense. Installment payment and settlement records represent future cash flow only.
